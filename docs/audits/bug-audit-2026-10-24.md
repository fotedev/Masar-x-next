## In short

We audited the entire project — web, mobile, desktop, and the database — with 30 independent hunt agents, and personally verified every critical and high finding by actually reading the code. **Things worked day-to-day because the current production environment is a "stale-lineage" build — but the project had real vulnerabilities.**

**Final outcome after remediation:** all five critical findings are closed (one turned out not to exist in production after direct introspection), most of the important high findings are fixed, and remediation surfaced a deeper root cause: **the quiz-attempts table was impossible to UPDATE in production** — meaning finishing any quiz was never being saved at all.

### C4 (spec 030) — the design that closed it

`finish_quiz_attempt(p_attempt_id, p_time_taken_seconds)` (SECURITY DEFINER, 011-style 42501 guard,
`FOR UPDATE` lock, idempotent `already_finished`): re-grades every `quiz_answers` row against
`quiz_questions.correct_answer` (overwriting client-sent `is_correct`), computes score/total
server-side, finalizes, rebuilds the `answers` jsonb authoritatively, returns the trusted numbers.
`trg_guard_quiz_attempt_score` blocks direct client UPDATEs of grading columns via the
`app.quiz_grading` GUC (same pattern as the 018 `extra_assets_entitled` guard). Web + mobile finish
flows call the RPC and display the returned values; guests untouched (zero attempt requests, locked
by e2e). `correct_answer` still ships and in-quiz instant feedback is unchanged (explicit non-goal).

**Verified live on prod:** direct score forge as the row's owner rejected with
`P0001: quiz attempt grading is managed server-side only (spec 030)`; nonexistent-id call returns
42501 `quiz attempt not found`; anon EXECUTE revoked; row data untouched by all tests.

## 🔴 The deepest discovery: H27's true root cause (corrects the audit)

Post-apply verification found prod `quiz_attempts` had **no `updated_at` column** while its own
pre-existing `tr_update_quiz_attempts_updated_at` trigger assigned `NEW.updated_at` — so **every
UPDATE to the table failed with 42703: quiz finishes NEVER persisted server-side on prod** (web and
mobile alike). The live table also lacked `status` (mobile's old finish wrote it) and
`last_updated_at`. This is the migrations.old-lineage drift striking at runtime: plpgsql binds
columns lazily, so the broken state "succeeded" until exercised. Fixed in #162 (add `updated_at`,
align 019 to the actual 10 live columns). The audit's wave-7 H27 diagnosis (offline startAttempt)
described the symptom path; the DB-level break was the deeper cause.
